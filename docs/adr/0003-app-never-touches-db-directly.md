# 앱은 DB에 직접 접근하지 않는다. DB는 서버(service role)만

iOS 앱은 로그인 전이든 후든 Supabase 테이블을 직접 읽거나 쓰지 않는다. 모든 데이터는 서버 API를 거친다. 그래서 모든 테이블에 RLS를 켜고, anon·authenticated 역할에는 정책도 테이블 권한도 주지 않는다. DB 접근은 서버의 service role만 한다. 앱이 Supabase에서 쓰는 것은 로그인(인증)뿐이다.

Supabase 앱은 보통 앱이 DB를 직접 읽고 RLS로 막는 구조라서, 이 결정은 처음 보면 의외일 수 있다. 우리가 그 구조를 쓰지 않는 이유는 anon 키가 앱 안에 들어가서 앱을 뜯으면 꺼낼 수 있기 때문이다. 직접 읽기를 열면 그 키로 서버를 거치지 않고 카드를 긁어갈 수 있다. 그러면 서버의 IP당 요청 제한·캐시(HANDOFF 3-7)와 무료/Plus 줄 노출 판단(세 번째 줄 잠금, HANDOFF 3-2)이 모두 우회된다.

절충안으로 "anon 읽기는 열고 세 번째 줄만 컬럼 권한으로 막기"도 검토했다. 하지만 요청 제한 우회는 그대로 남고, 컬럼을 추가할 때마다 공개 여부를 신경 써야 해서 버렸다. 열린 곳이 0이면 실수할 곳도 0이다.

## Consequences

- 로그인 없이 카드 보기(HANDOFF 3-2)는 서버의 카드 조회 API가 맡는다(다음 스펙 #15). 그 API가 생기기 전까지 앱은 카드를 볼 수 없다.
- 스키마 테스트가 "RLS 꺼진 테이블 0개", "anon·authenticated에 적용되는 정책 0개", "anon·authenticated로 모든 테이블 읽기·쓰기 거부"를 일반 규칙으로 검사한다. 새 테이블도 자동으로 검사된다.
- 나중에 유저 본인 데이터를 앱이 직접 읽어야 할 이유가 생기면(예: 실시간 구독), 이 ADR을 다시 열고 그 테이블만 `to authenticated` 정책으로 명시한다. 그때도 anon 정책은 만들지 않는다.
- 한 번 열면 다시 닫기 어렵다. 직접 읽기에 의존하는 앱 버전이 배포되면, 닫는 순간 그 버전이 깨진다.
