# 내 종목 규칙은 DB 트리거가 지킨다

무료 내 종목 3개, 교체(삭제) 하루 3회, 내 종목 이력 자동 기록(추가 전용), 다운그레이드 잠금, 타임존 변경은 다음 날부터 — 이 규칙들은 `my_stock`·`user_profile` 테이블의 트리거(`security invoker`, `search_path = ''`)가 지킨다. 쓰는 쪽은 `insert`/`delete`만 하고, 거절은 이름이 고정된 오류(`free_swap_limit`, `free_my_stock_limit`, `lock_by_plan_only`, `timezone_name`)로 받는다. 오류 메시지에 유저 데이터는 넣지 않는다(#8).

쓰는 서버가 둘이라서 이렇게 했다. 지금은 Python(GitHub Actions 배치)이고, 다음 티켓의 "내 종목 고르기" 화면은 Next.js 서버(TypeScript)가 쓴다. Python API 서버 하나에 규칙을 모으는 방법도 검토했다. 하지만 그러려면 지금 없는 상시 API 서버, 배포, 토큰 검증, 웹→Python 호출을 새로 만들어야 한다. DB 규칙은 어느 경로로 써도 우회할 수 없고, 기존 패턴(카드 수정 이력 트리거)과 같으며, 스키마 테스트로 바로 확인할 수 있다.

## Consequences

- 업무 규칙이 plpgsql에 있다. 숫자(3·3)는 SQL 상수이고, 무료만 해당한다. Plus는 개수·교체 제한이 없고 커버 범위(FK)가 상한이다.
- 무료 삭제 횟수는 AFTER 트리거가 이력을 쓴 뒤에 센다. 한 문장으로 여러 행을 지워도 넘지 않게 하기 위해서다. 같은 유저의 쓰기는 BEFORE 트리거가 프로필 행을 `for update`로 잠가 한 줄로 세운다.
- 같은 유저가 삭제와 플랜 변경을 동시에 하면 Postgres가 한쪽을 교착(`40P01`)으로 끊는다. 아무것도 반영되지 않으므로 닫힌 쪽으로 실패하고, 쓰는 쪽은 1회 다시 시도하면 된다.
- 웹 서버와 나중의 앱 API가 위 오류 이름에 기대게 된다. 이름을 바꾸면 그쪽도 같이 바꿔야 한다.
- ADR-0003과 함께 읽는다: 앱·브라우저는 이 테이블을 직접 읽거나 쓰지 않는다. "본인 데이터만"은 서버가 검증된 로그인 토큰의 유저 id로 거른다.
